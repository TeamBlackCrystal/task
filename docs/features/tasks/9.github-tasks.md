# GitHub↔タスク連携 仕様書

> ステータス: **Draft** / 作成日: 2026-05-27 / 改訂: 2026-09-02（データモデルを PR エンティティ分離へ変更）
> **PR #9b — 依存: [コア](/features/tasks/core)（PR #1）, [自動化](/features/tasks/automation)（PR #8）, [GitHub App 基盤](/features/tasks/github-app)（PR #9a）, [レビュー指摘](/features/review-findings)**

## 1. 概要

PR #9a で構築した GitHub App 基盤の上に、PR・コミット・ブランチとタスクの自動リンクを追加する。

コミットメッセージや PR タイトルに `KEY-N`（プロジェクトキー + 連番、例: `ENG-42`）を書くだけで自動リンクされ、`Closes ENG-42` を含む PR がマージされるとタスクが自動クローズされる。リンクされたコミットはタスクのアクティビティに並ぶ（TASK-140）。

> **なぜ `KEY-N` か**: GitHub 自身が `#N` を Issue 番号として使用するため、`#42` ではどちらを指すか曖昧になる。`ENG-42` のようなプロジェクトキー付き形式は GitHub Issues と衝突せず、Linear・Jira ユーザーにも馴染み深い。

### タスクをハブにする

GitHub 側の 3 つの実体（Issue / PR / コミット）は、それぞれ**タスクに**結ぶ。Issue と PR を直接結ぶ表は持たない。

```text
github_issue_links ──▶ tasks ◀── github_pull_request_links ──▶ github_pull_requests ◀── reviews
                         ▲                                              ▲
                         └── github_commit_links ──▶ github_commits ────┘ (任意)
```

- Issue はすでにタスクの GitHub 側の写し（1 対 1、[GitHub App 基盤](/features/tasks/github-app) §8）。PR もタスクに結べば、Issue との対応はタスク経由で自動的に取れる
- Issue を取り込んでいないプロジェクトでも PR / コミットのリンクは使える
- [レビュー指摘](/features/review-findings)のラウンド（`reviews`）は PR に付く。PR を独立した実体にすることで、レビュー指摘 → PR → タスクと辿れるようになる（今は `reviews` が `repo_owner / repo_name / pr_number` の生の組を控えているだけで、タスクとは無縁）

### 既存の設計との差分

旧 Draft は `task_github_links` 1 表に `link_type`（pull_request / commit / branch）で混載する設計だった。これをやめた理由:

- PR の状態（open / merged）や head は「PR 1 つに 1 つ」の属性で、タスクとの組ごとに持つと同じ PR が 3 タスクに付いたとき 3 行が食い違う
- `reviews` から PR を参照できない（`reviews` の側も生の組を持つ二重管理になる）
- コミットは SHA、PR は番号、と自然キーが違うものを NULL 混じりの UNIQUE で束ねることになる

## 2. データモデル

### `github_pull_requests`（PR）

| カラム | 型 | 制約 | 説明 |
|--------|-----|------|------|
| `id` | UUID | PK | |
| `project_id` | UUID | NOT NULL, FK→projects CASCADE | |
| `integration_id` | UUID | NULLABLE, FK→github_integrations SET NULL | 作成時点の連携。解除で NULL（行は残す） |
| `repo_owner` | VARCHAR | NOT NULL | 連携先リポジトリの控え。連携が無い（レビュー指摘の連携前ラウンド）場合は**空文字列** |
| `repo_name` | VARCHAR | NOT NULL | 同上 |
| `pr_number` | INT | NOT NULL | |
| `title` | VARCHAR | NOT NULL DEFAULT '' | 表示用。webhook / API で取得できたときだけ埋まる |
| `author` | VARCHAR | NOT NULL DEFAULT '' | GitHub の login。同上 |
| `state` | VARCHAR | NOT NULL DEFAULT 'unknown' | `open` / `closed` / `merged` / `unknown`（CLI の `review submit` だけで作られ、まだ webhook を受けていない） |
| `head_sha` | VARCHAR(40) | NULLABLE | 最後に観測した head。`review summary` の head 一致検査の補助 |
| `merged_at` | TIMESTAMPTZ | NULLABLE | |
| `created_at` / `updated_at` | TIMESTAMPTZ | NOT NULL DEFAULT now() | |

`UNIQUE (project_id, repo_owner, repo_name, pr_number)`。リポジトリを含める理由は
[レビュー指摘](/features/review-findings) §3 と同じで、連携先の差し替え後に旧リポジトリの
#10 と新リポジトリの #10 が同じ PR として続かないようにするため。空文字列を NULL に
しないのも同じ理由（Postgres の UNIQUE は NULL 同士を別物とみなす）。

`reviews` は `repo_owner / repo_name / pr_number` の 3 列をやめ、`pull_request_id`（FK→github_pull_requests RESTRICT）を持つ。
採番の UNIQUE は `(pull_request_id, round)` になる。`pr_title / pr_author` の控えは
`github_pull_requests.title / author` に移る。

### `github_pull_request_links`（PR ↔ タスク）

| カラム | 型 | 制約 | 説明 |
|--------|-----|------|------|
| `pull_request_id` | UUID | NOT NULL, FK→github_pull_requests CASCADE | |
| `task_id` | UUID | NOT NULL, FK→tasks CASCADE | |
| `closes` | BOOLEAN | NOT NULL DEFAULT false | クローズキーワード付きで参照されたか。マージ時の自動完了の対象 |
| `source` | VARCHAR | NOT NULL | `title` / `body` / `branch` / `manual`。再解析時に `manual` を消さないための区別 |
| `created_at` | TIMESTAMPTZ | NOT NULL DEFAULT now() | |

`PRIMARY KEY (pull_request_id, task_id)`。1 PR が複数タスクを閉じる、1 タスクに複数 PR、どちらも起きるので多対多。

### `github_commits`（コミット）

| カラム | 型 | 制約 | 説明 |
|--------|-----|------|------|
| `id` | UUID | PK | |
| `project_id` | UUID | NOT NULL, FK→projects CASCADE | |
| `integration_id` | UUID | NULLABLE, FK→github_integrations SET NULL | |
| `repo_owner` / `repo_name` | VARCHAR | NOT NULL | |
| `sha` | VARCHAR(40) | NOT NULL | 小文字 16 進 |
| `message` | TEXT | NOT NULL | 全文。表示は先頭行 |
| `author_login` | VARCHAR | NOT NULL DEFAULT '' | GitHub アカウントに解決できたとき |
| `author_name` | VARCHAR | NOT NULL | git の author 名（解決できないときの表示用） |
| `committed_at` | TIMESTAMPTZ | NOT NULL | |
| `pull_request_id` | UUID | NULLABLE, FK→github_pull_requests SET NULL | その PR に含まれるコミットとして観測されたとき |
| `created_at` | TIMESTAMPTZ | NOT NULL DEFAULT now() | |

`UNIQUE (project_id, repo_owner, repo_name, sha)`。rebase / force-push で同じ変更が別 SHA に
なった場合は別のコミットとして積む。履歴としてはそれが正しく、古い SHA を消す根拠も
無い。

### `github_commit_links`（コミット ↔ タスク）

| カラム | 型 | 制約 |
|--------|-----|------|
| `commit_id` | UUID | NOT NULL, FK→github_commits CASCADE |
| `task_id` | UUID | NOT NULL, FK→tasks CASCADE |
| `created_at` | TIMESTAMPTZ | NOT NULL DEFAULT now() |

`PRIMARY KEY (commit_id, task_id)`。

### `github_branch_links`（ブランチ ↔ タスク）

| カラム | 型 | 制約 |
|--------|-----|------|
| `id` | UUID | PK |
| `project_id` | UUID | NOT NULL, FK→projects CASCADE |
| `task_id` | UUID | NOT NULL, FK→tasks CASCADE |
| `repo_owner` / `repo_name` | VARCHAR | NOT NULL |
| `branch` | VARCHAR | NOT NULL |
| `created_at` | TIMESTAMPTZ | NOT NULL DEFAULT now() |

`UNIQUE (task_id, repo_owner, repo_name, branch)`。ブランチは状態も本文も持たないので
実体表を分けない。`delete` イベント（ref_type=branch）で消す。

### アクティビティ

コミットのリンクは `task_activities` に `event_type = "github_commit_linked"` で 1 行積む
（`payload`: `sha` / `message` 先頭行 / `author_login` / `author_name` / `html_url`）。
PR も同様に `github_pull_request_linked` / `github_pull_request_merged` を積む。
`user_id` は GitHub の login が連携済みユーザーに解決できたときだけ入れ、それ以外は NULL。
アクティビティは追記のみで、リンクが消えても行は残す（履歴）。

## 3. マイグレーション

1 本のマイグレーションで次を行う。順序が重要（`reviews` の付け替えは PR 行を先に作る）。

```sql
CREATE TABLE github_pull_requests (...);   -- §2
CREATE TABLE github_pull_request_links (...);
CREATE TABLE github_commits (...);
CREATE TABLE github_commit_links (...);
CREATE TABLE github_branch_links (...);

-- 既存の reviews から PR 行を起こす（DISTINCT な組ごとに 1 行。title/author は控えを写す）
INSERT INTO github_pull_requests (id, project_id, integration_id, repo_owner, repo_name, pr_number, title, author, state)
SELECT gen_random_uuid(), project_id, max(integration_id::text)::uuid, repo_owner, repo_name, pr_number,
       max(pr_title), max(pr_author), 'unknown'
FROM reviews GROUP BY project_id, repo_owner, repo_name, pr_number;

ALTER TABLE reviews ADD COLUMN pull_request_id UUID REFERENCES github_pull_requests(id) ON DELETE RESTRICT;
UPDATE reviews r SET pull_request_id = p.id FROM github_pull_requests p
 WHERE (r.project_id, r.repo_owner, r.repo_name, r.pr_number) = (p.project_id, p.repo_owner, p.repo_name, p.pr_number);
ALTER TABLE reviews ALTER COLUMN pull_request_id SET NOT NULL;
ALTER TABLE reviews DROP CONSTRAINT <uq_reviews_round>;
ALTER TABLE reviews DROP COLUMN repo_owner, DROP COLUMN repo_name, DROP COLUMN pr_number,
                    DROP COLUMN pr_title, DROP COLUMN pr_author, DROP COLUMN integration_id;
ALTER TABLE reviews ADD CONSTRAINT uq_reviews_round UNIQUE (pull_request_id, round);

CREATE INDEX idx_gh_pr_links_task ON github_pull_request_links(task_id);
CREATE INDEX idx_gh_commit_links_task ON github_commit_links(task_id);
CREATE INDEX idx_gh_commits_pr ON github_commits(pull_request_id);
CREATE INDEX idx_gh_branch_links_task ON github_branch_links(task_id);
```

`reviews.integration_id` の意味（連携解除で NULL になる）は `github_pull_requests.integration_id` が引き継ぐ。

## 4. タスクへの自動リンク

### パターン一覧

PR タイトル・PR 本文・コミットメッセージ・ブランチ名から `KEY-N` を正規表現でパースする。

正規表現: `\b([A-Z][A-Z0-9]{1,9})-(\d+)\b`（大小文字不問でマッチさせ、`KEY` は大文字に正規化して照合）

| パターン | 例 | 動作 |
|---------|-----|------|
| `KEY-N`（タイトル / メッセージ） | `fix: ログインバグ修正 ENG-42` | タスク ENG-42 にリンク追加 |
| 複数 `KEY-N` | `feat: OAuth ENG-42 ENG-43` | タスク ENG-42 と ENG-43 両方にリンク追加 |
| 異なるプロジェクト | `feat: OAuth ENG-42 BACK-7` | 各プロジェクトのタスクにそれぞれリンク |
| ブランチ名 | `feat/ENG-42-oauth` | タスク ENG-42 にブランチリンク追加 |
| クローズキーワード + `KEY-N` | `Closes ENG-42` / `Fixes ENG-42` / `Resolves ENG-42` | `closes = true` でリンク。PR マージ時にタスク ENG-42 を自動クローズ |

**クローズキーワード:** `Closes` / `Close` / `Closed` / `Fixes` / `Fix` / `Fixed` / `Resolves` / `Resolve` / `Resolved`（大小文字不問。GitHub と同じ集合）
PR タイトルおよび PR 本文の両方が対象。GitHub 自身の `Closes #N`（Issue クローズ）と構文が異なるため衝突しない。

### KEY-N の解決

`KEY-N` はまず `KEY` でテナント内のプロジェクトを特定し、その `seq_id=N` のタスクを探す。
`KEY` が不明またはタスクが見つからない場合はリンク追加をスキップ（エラーにしない）。
1 つのコミット / PR が複数プロジェクトのキーを含む場合、それぞれのプロジェクトのタスクへリンクする。

**リンクできるのは、webhook を受けた連携（`github_integrations`）と同じテナントのプロジェクトだけ。**
リポジトリは 1 プロジェクトに連携されるが、キーの解決はテナント内の全プロジェクトに及ぶ
（`ENG-42 BACK-7` のように複数プロジェクトを 1 PR で触ることは普通にある）。
別テナントのキーは同じ文字列でも解決しない（他テナントのタスクへ外部から行を足せてしまう）。

抽出は `service::github::task_refs` に置き、固定テストで次を確認する:
`TASK-140` / `task-140` / `[TASK-140]` / `feat/TASK-140-foo` / 複数キー / 別プロジェクト混在 /
`TASK-1400` が `TASK-140` に誤マッチしない / `SHA256-1` のような偽陽性の扱い（KEY として
解決できなければ捨てるだけなので許容） / クローズキーワードの有無で `closes` が変わる。

### GitHub Issue 経由の解決

PR 本文の `Closes #12`（GitHub Issue 番号）は、同じリポジトリの Issue #12 が
`github_issue_links` でタスクに結ばれていれば、そのタスクへの `closes = true` リンクとして扱う。
Issue を取り込んでいるプロジェクトでは `KEY-N` を書かなくても GitHub の流儀のままでリンクされる。

## 5. 受信する GitHub Webhook イベント

PR #9a の webhook エンドポイント（`POST /v1/github/webhook`）は `X-GitHub-Event` を見ずに
ジョブへ積む作りになっている。本 PR は `job::github_webhook::process` に `push` /
`pull_request` / `create` / `delete` の分岐を足す。

**Webhook の登録作業は無い。** GitHub App の webhook は App 側の設定 1 つで、インストール先
リポジトリのイベントは自動でこのエンドポイントに届く。必要なのは App の
設定で Permissions に **Contents: Read** / **Pull requests: Read**、Subscribe to events に
**Push** / **Pull request** / **Create** / **Delete** を加えることだけ（[GitHub App 基盤](/features/tasks/github-app) §4 の
権限表に沿う）。権限を増やした後は、既存インストールのオーナーが GitHub 上で承認するまで
新しいイベントは届かない。

### 冪等性設計

GitHub は障害時に同一イベントを複数回送信することがある。`X-GitHub-Delivery` ヘッダー（配信固有 UUID）を使って二重処理を防ぐ。

```text
受信時:
  delivery_id = X-GitHub-Delivery ヘッダー値
  Redis SET NX gh_delivery:{delivery_id} "1" EX 86400
    → SET 成功（初回）: 通常処理へ
    → SET 失敗（重複）: 即 200 OK を返して処理をスキップ
```

実体（`github_pull_requests` / `github_commits`）とリンク表の INSERT は常に UPSERT で行い、
再送でも行が増えないようにする。アクティビティ行は「リンク表に行が**新規に**入ったとき」だけ
積む（UPSERT の `xmax = 0` で判定）。

`pull_request.closed`（merged=true）時のタスク遷移は、タスクが既に done 系ステータス（`is_done_state = true`）の場合はスキップして二重遷移を防ぐ。

### イベント一覧

| GitHub イベント | 処理内容 |
|---------------|---------|
| `push` | `commits[]` ごとに `github_commits` を UPSERT し、メッセージをパースしてリンク + アクティビティ。`deleted = true` / `forced = true` は無視しない（新 SHA を積むだけ） |
| `pull_request.opened` | `github_pull_requests` を UPSERT（title / author / state / head_sha）。タイトル + 本文 + head ブランチ名をパースしてリンク |
| `pull_request.edited` | タイトル・本文を再解析。`source in (title, body)` のリンクを作り直す（`manual` / `branch` は触らない） |
| `pull_request.synchronize` | `head_sha` を更新。`GET /pulls/{n}/commits` で `github_commits.pull_request_id` を埋める |
| `pull_request.closed`（merged=true） | `state → merged`、`merged_at`。`closes = true` のリンク先で未完了のタスクを完了ステータスへ遷移し、Automation `github_pr_merged` トリガーを発火 |
| `pull_request.closed`（merged=false） | `state → closed` |
| `pull_request.reopened` | `state → open` |
| `create`（ref_type=branch） | ブランチ名をパースし `github_branch_links` を UPSERT |
| `delete`（ref_type=branch） | 該当の `github_branch_links` を削除 |

`issues` イベントは従来どおり（[GitHub App 基盤](/features/tasks/github-app)）。

### 過去分の取り込み

webhook は連携後のイベントしか拾わない。初回は過去の PR / コミットを遡らない
（`POST /github/import` は Issue 専用のまま）。必要になったら別 Issue で
「open な PR と既定ブランチの直近 N コミット」を取り込む拡張を足す。

## 6. CLI との合流

`task review submit` は `pr` 番号を受け取っている。ラウンド作成時に
`github_pull_requests` を `(project_id, 現在の連携先, pr)` で **UPSERT してから**
`reviews.pull_request_id` に結ぶ。webhook をまだ受けていなければ `state = unknown` の行が
先にできる。これで CLI から出たレビュー指摘も、後から届いた webhook で同じ PR 行に合流する。

`review summary` の head 一致検査は従来どおりラウンドの `head_sha` を見る
（`github_pull_requests.head_sha` は表示用の補助であり、ゲートの根拠にはしない。webhook の
遅延で古い値になりうる）。

## 7. GitHub 側へのフィードバック

PR 作成時に、リンクされたタスクへの URL をコメントとして PR に自動追加する（権限 `pull_requests: write` が必要）。

```markdown
---
🔗 Linked Task: [ENG-42 OAuth 対応を実装する](https://app.example.com/projects/.../tasks/42)
```

[レビュー指摘](/features/review-findings) §7 の要約コメントと同じ PR に 2 本のコメントが並ぶ。
統合は将来の課題とし、本 PR ではマーカー（`<!-- task:linked -->`）で自分のコメントを見分けて
再解析時に**同じコメントを更新**するところまでにする。

## 8. API

| メソッド | パス | 説明 |
|---------|------|------|
| `GET` | `/tasks/{id}/github` | タスクに紐付いた PR / コミット / ブランチ（3 配列を 1 レスポンスで返す） |
| `POST` | `/tasks/{id}/github/pull-requests` | 手動で PR をリンク（`source = manual`） |
| `DELETE` | `/tasks/{id}/github/pull-requests/{pull_request_id}` | PR のリンクを外す（PR 行自体は消さない） |
| `DELETE` | `/tasks/{id}/github/commits/{commit_id}` | コミットのリンクを外す |
| `DELETE` | `/tasks/{id}/github/branches/{link_id}` | ブランチのリンクを外す |
| `GET` | `/github/pull-requests/{pull_request_id}` | PR 詳細（リンク先タスク一覧 + レビューラウンド一覧）。レビュー画面から辿る用 |

`POST /tasks/{id}/github/pull-requests` リクエスト:

```json
{ "pr_number": 87, "closes": false }
```

リポジトリはプロジェクトの**現在の連携先**で確定する（`repo` は受け取らない。連携が無ければ 409）。
PR 行が無ければ `state = unknown` で作り、`GET /pulls/{n}` が引ければ title / author / state を埋める。
コミットとブランチの手動リンクは無し（コミットは `KEY-N` をメッセージに書き直せない事情があるが、
`git notes` 相当を持ち込むより手動 PR リンクで代替できる）。

権限は task の編集権限に従う（プロジェクトメンバー）。webhook 経由のリンクはシステムが行うので権限検査を経ない。

`ReviewResponse` / `ReviewedPullRequest`（[レビュー指摘](/features/review-findings) §5）は
`pull_request_id` と `linked_tasks: [{ id, seq_id, key, title }]` を返すようになる。
`pr_number / repo_owner / repo_name / pr_title / pr_author` のフィールドは PR 行から取って同じ名前で返す（CLI の `--repo` 絞り込みは維持）。

## 9. フロントエンド（Phase B）

### タスク詳細「GitHub」セクション

```text
┌─────────────────────────────────────────────┐
│ GitHub                              [+ PR をリンク] │
├─────────────────────────────────────────────┤
│ Pull Requests                                │
│  ✅ #87  feat: OAuth 対応 ENG-42  [Merged] 未解決なし │
│  🔄 #91  fix: エラーハンドリング  [Open]  2 件が未解決 │
│                                             │
│ Commits                                     │
│  a3f92c1  fix: トークン期限切れを修正  yupix │
│  e7b81d4  feat: GitHub App 初期実装    yupix │
│                                             │
│ Branches                                    │
│  feat/ENG-42-oauth                          │
└─────────────────────────────────────────────┘
```

## 10. 実装の分割（1 関心 = 1 PR）

1. **PR エンティティ + `reviews` の付け替え**: §2 の `github_pull_requests` と §3 のマイグレーション、`review submit` の UPSERT（§6）、`ReviewResponse` の形の維持。挙動は変わらない（回帰テストは既存の reviews 統合テストがそのまま通ること）
2. **抽出 + コミット / PR / ブランチのリンク + webhook**: `task_refs`、残りのテーブル、§5 のイベント処理、アクティビティ。**TASK-140 はここで閉じる**
3. **手動リンク API + フロントエンド**: §8 / §9
4. **GitHub へのコメント**（§7）。Automation `github_pr_merged` は PR #8 の実装状況に合わせる

## 11. 受け入れ条件（テスト観点）

- `task_refs`: §4 の固定テスト一式
- webhook: `push` で 1 コミット / 複数コミット / `KEY-N` 無し / 同じ delivery の再送（行が増えない・アクティビティが増えない） / 別テナントのキー（リンクされない）
- `pull_request.closed` merged: `closes = true` のタスクだけ完了する / 既に完了のタスクは遷移しない / `closes = false` は触らない
- `pull_request.edited`: 本文から `KEY-N` を消すと `body` 由来のリンクが消え、`manual` は残る
- `reviews` の付け替え: 既存ラウンド（連携前の空文字列リポジトリを含む）が移行後も同じ `pr_number` / `round` で一覧に出る。連携先差し替え後の同番号 PR が別の PR 行になる
- API: 手動リンクの 201 / 連携なし 409 / メンバー外 403 / 他プロジェクトのタスク 404
